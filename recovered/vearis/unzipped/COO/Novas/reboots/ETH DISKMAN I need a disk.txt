NUMA Nodes in Multi-Socket VM Instances:

gVNICs are often deployed in VMs with multiple CPUs or multi-socket configurations. Google Cloud offers different VM types (such as N2 or C2) that provide multiple cores, which could be spread across NUMA nodes.
NUMA affects the memory access performance based on where a CPU core is located relative to the memory it accesses. For optimal performance, you want each CPU to access its local memory node (to minimize cross-node memory access latency).
Jumbo Frames (MTU 8896):

Jumbo frames can help reduce overhead, but require that your network infrastructure supports them end-to-end (i.e., between gVNICs, routers, load balancers, and VPCs).
Ensure the VPCs, routers, and all VM configurations are optimized to handle these larger MTUs without fragmentation or bottlenecks.
Multiple gVNICs:

With 8 gVNICs, you're likely aiming for high network throughput, so it's important to configure each NIC on a separate NUMA node to reduce contention and maximize bandwidth.

VM Sizing and NUMA Node Affinity:

```bash

```

For example, if you are using `eth0`, identify its IRQ number and assign it to CPUs 0-10:

### 2. **Optimize Kernel for NUMA**

- **Enable NUMA-aware Memory Allocation**:
- You can instruct the kernel to allocate memory based on NUMA locality by enabling **NUMA scheduling** in the kernel. This ensures that memory is allocated closer to the CPU that's using it, reducing cross-node memory access. This is done by setting the `numactrl` flags to prefer local node memory:
